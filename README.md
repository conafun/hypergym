## 这是什么？

HyperGym 是一套**手环 + 手机**协同的力量训练记录系统：

- **手环端**（小米手环 10 Pro / Vela OS）：在手环上选择动作、记录每组重量和次数，长按历史记录一键发送到手机。
- **手机端**（Android / HyperOS）：接收数据后，以暖橙白卡风格的现代 UI 展示训练统计、肌群分布、训练日记和 1324 个标准动作的教学库。

当前版本：**手机端 v3.1.18**（versionCode 25） / **手环端 v1.0.70**（versionCode 70），底部 5 个页签：**数据 / 肌群 / 日记 / 动作 / 传输**。

> ⚠️ **手环 rpk 的签名方式已定死，禁止修改。**
> 一旦 rpk 的签名与手机 APK 不一致，两个设备会**彻底无法通信**，而且这个问题**不留任何源码痕迹**。
> 动手前请先读 [`SIGNING.md`](SIGNING.md)。

`demo-package/` 下是本机打好的安装包（**不入库**，见 `.gitignore`）：`HyperGym-release.rpk`（手环）、`HyperGym-Phone-debug.apk`（手机）。用根目录的 `build-debug.ps1` 一键重新产出。

## 功能特性

### 📊 数据总览（数据页）

![数据页](screenshots/data.png)

- **训练热力图**：周历 + 「展开整月」月历网格。色阶按**名次**分 4 档**实色**（不是"当天 ÷ 最大值"），所以即使各天数据很接近也能一眼看出多少——否则只要有一天特别猛，其余天就全被压成同一片浅色。未训练用**冷灰**、已训练用**暖橙**，靠**色相**区分而不只是明暗。卡片内只有热力图本身，不加任何说明文字。
  - **收起时是一整周（周一→周日）**，取**今天所在的那一周**——和展开后的月历同一套列排布，
    所以收起/展开看到的是同一周，不会出现"收起显示上周、展开显示本周"的错位
  - 今天**之后**的格子沿用月历口径：**灰块占位、不写日期、不可点**（未来的日子没有数据可看）
  - 展开态左上角还有 **‹ 年月 › 左右翻月**；今天用主色描边、点选的那天用白色描边
- **页头**：标题 + 「共 N 天训练记录」；右上角月份 pill 点开是**横向滚动的月份选择器**——
  选某个月会同时把区间切到「月」、展开月历、并把该月最后一天设为选中日。
- **当天训练卡片**：展示所选日期的动作明细 + 当日总容量。**同一动作的不同重量合并在一块**——动作名只出现一次，组内按重量分行（每行左侧重量、右侧该重量的容量，下方是该重量的次数标签），右侧给出该动作的组数与合计容量，不再重复占行。
- **PR 纪录卡片**（在「当天训练卡片」下方）：列出**每个动作的历史最高重量**，并换算成可直接上杠的配重。
  - **肌群可折叠**（默认全部收起）：收起时每个肌群一行 —— `色点 + 肌群名 + 动作数 + ▸`，整张卡片约 240px；
    点某一行才展开它下面的动作，**可同时展开多个**
  - 展开后**每个动作一行**，动作行只用**肌群色点**标识归属、不重复写肌群名；组内按**重量降序**
  - 每行两个数字：**PR**（主题橙）与**实际用**（主文字色/黑），两者之间留 **10dp 固定间隙**——
    这是两类量纲不同的数（前者是历史最高，后者是今天该上的配重），范围文字最长（如 `52.5–55.0kg`）时也不能贴在一起
  - **实际用** = `PR × 下限%` 与 `PR × 上限%`，各自取到最近的 **2.5kg**（四舍五入，杠铃片最小组合单位），
    两端相同则只显示一个值；结果固定 **1 位小数**，所以只会出现 `.0` / `.5`（如 `50.0–52.5kg`）
  - 卡片右上角两个**百分比输入框**（默认 65 / 70）可手输，改完下面所有数字立即重算；
    该设置**持久保存**（SharedPreferences），重开 App 仍是上次输入的值
  - **只显示有配重的动作**：自重（0kg）按口径不算 PR，因此不出现
  - 始终基于**全部历史**，不随页面上方的「周 / 月 / 全部」变化

![PR 纪录卡片](screenshots/pr_card.png)

> 点肌群行展开该肌群的每个动作：左边橙色是该动作的历史最高（PR），右边黑色是
> `PR × 65%~70%` 换算出的实际用范围（各自取到最近的 2.5kg）。两个数字之间留 10dp 固定间隙。

- **范围切换**（pills 位于 PR 卡之后）：**周 / 月 / 全部**，切换英雄卡、统计卡与容量趋势。三档的实际口径：

  | 档位 | 取数范围 | 说明 |
  |---|---|---|
  | 周 | **最近 7 天**（今天往前数 7 天） | ⚠️ **不是自然周**，但英雄卡标题写的是「本周总容量」（见[已知问题](#已知问题)） |
  | 月 | 所选月份的 **1 号 → 今天** | 月份由页头右上角的月份 pill 切换，可选历史月份 |
  | 全部 | 全部历史 | — |

  环比也是按同一口径取上期：周 = 近 7 天 vs 前 7 天；月 = 本月 vs 上月同期；全部 = 最近 4 周 vs 再前 4 周。
- **英雄卡**：总容量（标题随档位变为「本周 / X月 / 累计总容量」）+ 环比 ↑/↓% + 「N 次训练」。
- **统计卡片**：两张 —— **训练次数**、**总组数**。
- **容量趋势卡**：容量柱状图，横向可滚动、**默认滚到最右端**（优先显示最近的数据），柱顶标数值。

### 💪 肌群分析（肌群页）

![肌群页](screenshots/muscle.png)

- **动作数据汇总**：按天分组的**细柱状图**，同一天不同动作不同色；**默认滚动到最右端**（优先显示最近几天，而不是最早的几天）；**点击某一天的柱状图**，卡片底部按当天数据显示图例（可换行，两行内完整展示），再点可收起。
- **数据透视卡片**（页面第 2 张卡，可自定义）：像数据透视表一样组合维度与指标——
  - **X轴维度**：日期 / 周 / 肌群 / 动作
  - **Y轴指标**：总容量 / 总组数 / 总次数 / 平均重量 / 平均次数
  - **聚合方式**：总和 / 平均
  - **单项 / 多项**：单项显示一条汇总序列；多项按「明细维度」（动作 / 肌群）拆成多条彩色序列
  - **图表类型**：柱状 / 折线，**柱从底部生长、折线从左向右展开**的微动画
  - **横轴只标首尾两个日期**：数据一多逐点标注会全部挤在一起，中间的点改为点击查看
  - **点击图上任意一根柱/点**：下方直接列出该点各序列的数值（再点一次取消选中），并在图上高亮该点的竖线与圆点
  - **默认显示最近的数据**：数据变化后自动滚到最右端
  - **图例可点选筛选**：点图例里的某一项只看该序列（再点取消），卡片上会标出「已筛选：X」
  - X / Y 轴是**下拉菜单**，聚合方式 / 单项多项 / 图表类型是**分段 pill**

![肌群占比](screenshots/muscle_pie.png)

- **区间切换**（在页头下方、所有卡片之前）：**周 / 月 / 全部**，按**自然周期**取——**周 = 本周一 ~ 周日**，**月 = 本月整月**，**全部 = 全部历史数据**。选「全部」时，下面的数据透视与肌群占比都改用全部数据一起分析。
- **肌群占比**：甜甜圈图（中心显示区间总容量）+ 各肌群占比清单（百分比 + 容量）；
  标题随区间变为「本周 / 本月 / 全部肌群占比」。
  配色用的是**手环那套部位色**（`GROUP_COLORS` —— 胸橙 / 肩浅橙 / 背天蓝 / 腿柔绿 / 臂淡紫 / 核心蓝），
  与上面两张卡片的 `ChartPalette` 不是同一套：占比按**部位**上色，颜色和数据页 PR 卡片的色点一致。

### 📖 训练日记（日记页）

![日记页](screenshots/diary.png)

- 按日期倒序展示每天训练详情，每张卡片固定 **216dp 高的明细区**（约 3 个动作的高度），超出部分**卡片内上下滚动**。
- 与数据页保持一致：**同一动作的不同重量合并在一块**显示，动作名不再重复出现。
- **PR（个人纪录）徽章**（`🏆 动作名 值kg`）自动识别并标记 —— 只标**打破此前纪录**的那一天，**首次记录不算 PR**。
- **长按卡片晃动 + 右上角红色 ✕**：进入删除态的卡片会轻微摇晃（±2°）并显示 26dp 的红色 ✕；
  再长按一次或点卡片退出删除态。⚠️ **点 ✕ 立即删除、没有二次确认**。
  删除后**数据 / 肌群 / 日记页联动刷新**，对应日期的 JSON 行也从 `records-NNNN.jsonl` 数据文件中同步移除。

### 🏋️ 动作库（动作页）

![动作库](screenshots/exercise.png)

- 内置 **1324 个标准健身动作**（**纯中文**名称 + 分步教学 + 演示视频 + 图示），与手环动作列表**完全解耦**。
- 支持按肌群分类筛选（全部 / 胸 / 肩 / 背 / 腿 / 臂 / 核心 / 有氧 / 颈）+ 关键词搜索（按名称包含、不区分大小写）。
  列表项左侧是 56dp 缩略图，右侧是「分组 · 目标肌群 · 器材」。
  > 分类里还会产出「**其他**」，但筛选条里没有这一项 —— 这类动作只在「全部」下出现。
- 点击动作进入详情（同页切换）：**训练信息**（部位 / 目标肌群 / 主肌群 / 次要肌群 / 器材）+ **分步教学** + **1:1 方形视频演示**（ExoPlayer 本地 mp4 单曲循环、无控制器、无声自动播放）。

![动作详情](screenshots/exercise_detail.png)

### 📡 数据传输（传输页，原「诊断」）

![传输页](screenshots/transfer.png)

- 蓝牙连接状态实时显示。
- **P/S 调试码日志**，方便排查：**P 码 20 个（P01–P19，含 P02b）** 是互联链路，
  **S 码 9 个（S01–S08，含 S02r）** 是本地存储（后端 / 载入 / 落盘 / 删除）。
  两组逐条对照见 [`INTERCONNECT-GUIDE.md`](INTERCONNECT-GUIDE.md) §5。
- **SAF 安全目录存储**（卸载重装数据不丢）为主，内部存储兜底。
- 操作按钮：重连 / 测试发送（主色一行），清除 / 数据目录 / 重扫目录（白卡一行）。
  > **「清除」只清界面上的原始消息缓存，不会删除任何训练数据文件。**

    [`INTERCONNECT-GUIDE.md`](INTERCONNECT-GUIDE.md) §6 的 `pr-sync`。
    > 配色说明：**刻意不用绿色** —— `#30d158` 是大号重量数字的颜色，眯眼看容易把这行误读成
    > "当前要举的重量"。白色与动作名同色、黑底对比度 21:1，既清楚又不会与可选重量混淆。

    **长按重量数字 = 退出应用**（返回上一个应用）。
- **屏1 · 记录列表**：顶部是当前时间（每 30 秒刷新一次）；显示已加入计划的项目与已完成组数；
  点击项目开始计次（`-` / 次数 / `+` / 确认 / 取消，**默认 10 次，下限 1、无上限**）；
  长按项目编辑重量（`- / +` / 确定 / 删除，**只对「一组都还没完成」的项目生效**，重量可减到 0 显示成「自重」，且编辑时不校验上限）；
  「结束」保存并**回到屏2「今日数据」**（不是汇总页 —— 汇总页未注册路由，见[已知问题](#已知问题)）。
- **屏2 · 今日数据**：今日各动作的训练明细 + 底部 `总 Nkg`；自重动作显示为 `自重×N`。
- **屏3 · 历史**：按日期列出历史训练（每条含动作与容量），底部「本月 X 天 · 总 Xkg」；
  **长按日期即发送当天数据到手机**（成功/失败/当天无数据都有提示）。
- **屏4 · 联调诊断**：B00/B01… 调试码日志（**只保留最近 30 行**）+「诊断 / 发Ping / 重连」按钮；
  进入应用 2.5 秒后会自动跑一次诊断，手动「重连」后再跑一次。
- **训练完成 · 汇总**（`pages/summary`，**当前不可达**）：展示本次「动作 / 总组数 / 总容量」+ 每个动作的逐组明细，
  底部「返回主页」。页面本身完成度很高，只是没注册进路由 —— 属于死代码。

## 系统架构

```
┌────────────────────────────────────────┐
│          小米手环 10 Pro                │
│          (Vela OS 快应用)               │
│                                        │
│  屏0 选动作/重量 → 屏1 计次 → 屏3 发送  │
│  本地落盘 internal://files/             │
│           training_data.json           │
│           (version 2: records + prs)   │
└───────────────┬────────────────────────┘
                │  @system.interconnect
                │  (XMS Wearable SDK)
                │
   ① 手环 → 手机   training-records   训练记录（当天全量）
   ② 手机 → 手环   pr-sync            每个动作的历史最高重量（全量）
   ③ 双向         ping / ping-reply   连通性自检（屏4 按钮触发）
                │
                ▼
```

## 快速开始

### 手机端（Android App）

**环境要求：**

- JDK 21
- Android SDK（compileSdk 36, buildTools 36.1.0）
- Gradle 8.2（仓库自带 wrapper，无需另装）
- **`phone-app/keystore.properties`**：签名口令文件，`app/build.gradle` 在配置阶段会**无条件读取**，
  缺了直接构建失败（文件与 `keystore/` 一并入库；签名约束见 [`SIGNING.md`](SIGNING.md)）

**构建步骤：**

```bash
# 进入手机端项目目录
cd phone-app

# 设置环境变量（Linux/Mac）
export JAVA_HOME=/path/to/jdk21
export ANDROID_HOME=/path/to/android-sdk

# 构建 Debug APK（日常自用推荐，版本号用 version.properties 的当前值）
./gradlew assembleDebug

# 构建 Release APK
./gradlew assembleRelease

# APK 输出路径
# phone-app/app/build/outputs/apk/debug/app-debug.apk
# phone-app/app/build/outputs/apk/release/app-release.apk
```

> Windows 用 `gradlew.bat` 替换 `./gradlew`。
>
> ⚠️ **`assembleRelease` 会先自增版本号再构建**：读 `version.properties` → `versionCode +1`、`patch +1`
> → **写回文件** → 用新版本号构建。所以跑一次 release，产出的是**下一个版本**（例如仓库当前是
> 3.1.18/25，跑完会得到 **3.1.19/26** 且 `version.properties` 已被改写）。
> 日常出 debug 包不会自增；`build-debug.ps1 -Bump` 是另一套（走 `assembleDebug`，只 +1 一次）。

### 手环端（Vela 快应用）

**环境要求：**

- Node.js >= 8.10
- aiot-toolkit >= 2.0.5

**构建步骤：**

```bash
cd miband10pro-trainer
npm install
npm run release  # 发布 rpk 包（必须用 release，见下方警告）
```

> ⚠️ **装到手环上的 rpk 不要用 `npm run build` 打包。**
> `aiot` 在 development 模式下，若找不到 `sign/debug/` 与 `sign/private.pem`，会**静默回退到
> aiot-toolkit 自带的调试证书**去签名。这样打出的 rpk 与手机 APK 签名不一致，
> 手环与手机会**彻底无法通信**（`system.interconnect` 直接拒绝握手），而且这个问题
> **源码 diff 查不出来**（证书不在源码里）。只有 `release`（production 模式）才会用
> `sign/release/` 里那张与手机一致的证书。详见 [`SIGNING.md`](SIGNING.md)。

### 一键构建双端（本机）

仓库根目录的 `build-debug.ps1` 封装了本机构建链（`.research/` 内的 JDK 21 / Gradle / Android SDK）：

## 数据流详解

### 传输协议（三条消息）

| # | 方向 | `type` | 内容 | 触发时机 |
|:--:|---|---|---|---|
| ① | 手环 → 手机 | `training-records` | 当天的**全量**训练记录（`date` + `records`） | 屏3 长按某个日期 |
| ② | 手机 → 手环 | `pr-sync` | 每个动作的历史最高重量（全量表，约 28 项） | 手机把 ① 落盘成功后**立刻回发** |
| ③ | 双向 | `ping` / `ping-reply` | 连通性自检 | 屏4「发Ping」按钮；手环也会自动跑诊断 |

> ③ 的细节与判定速查见 [`INTERCONNECT-GUIDE.md`](INTERCONNECT-GUIDE.md) §5 / §6。

**① 手环 → 手机**：

```json
{
  "type": "training-records",
  "date": "2026-08-15",
  "records": [
    {
      "exercise": "杠铃深蹲",
      "weight": 80,
      "sets": [
        { "set": 1, "reps": 8, "volume": 640 },
        { "set": 2, "reps": 8, "volume": 640 },
        { "set": 3, "reps": 6, "volume": 480 }
      ]
    }
  ]
}
```

**② 手机 → 手环**（`pr-sync`，每次全量、无增量与版本令牌）：

```json
{ "type": "pr-sync", "prs": { "卧推": 80, "杠铃深蹲": 75, "高位下拉": 38 } }
```

手机端**不维护"已下发过什么"的镜像**（PR 每次由 `StatsEngine.bestWeights(全部历史)` 现算），
所以手环重装、数据丢失、两端不一致都会在下一次下发时整体覆盖修正。

### 两端的本地存储

**手环端**：`internal://files/training_data.json`，**全量覆盖写**，`version: 2`：

```json
{
  "app": "strength-trainer",
  "version": 2,
  "records": { "2026-10-01": [ { "exercise": "卧推", "weight": 70, "sets": [ … ] } ] },
  "prs": { "卧推": 80 }
}
```

- 手环保存时**也会按 (动作名, 重量) 合并**到当天已有记录并重排组号（与手机同一套规则）
- 老文件没有 `prs` 字段 → 读出来是空表 → 下次同步自动补齐，不需要额外的判断代码
- **保护位**：读文件解析失败时置 `readBroken` 并**拒绝一切保存**（宁可本次保存失败，也不覆盖原文件）；
  只有「文件不存在」（首次使用）不置位 —— 这是 v3.1.10 修掉的一次真实丢数据路径

**手机端**：JSONL 分片 + 内存索引。

- **合并**：以 `date` 定位当天，再按 **(动作名, 重量)** 合并——payload 里出现的键**替换**成 payload 的组列表，
  payload 里没有的键**原样保留**；同键的「组」按 (次数, 容量) 做**多重集合并**。
  于是「同一天分多次传输」会**累加**（先传 7 个动作、再传 3 个 → 共 10 个），
  「重复发送同一份」是**幂等**的（不会翻倍），手环中途丢数据时手机上已有的组**也不会被吃掉**。
  *（旧版是"同日期后到覆盖先到"，会把先传的数据整体抹掉——这正是曾经丢数据的根因。）*
- **分片**：`records-NNNN.jsonl`，每片 **30 行**；一行 = 一整天（日期做主键），所以**一片约 30 天**。
- **写盘**：append-only，写入后**逐行 `fsync`**；只有压缩 / 删除 / 切换目录才全量重写。
- **压缩**：总行数 **> 1200** 时自动重写（去重后重新分片）。
- **多线程**：所有读写都排在**单线程队列**里串行执行，`days` 索引同步读、单线程写。
- **持久化**：SAF 目录（用户授权的公共文件夹）为主，**卸载重装数据不丢**；没选目录时落到内部存储
  `filesDir/hypergym/`（卸载即丢）。
  > ⚠️ SAF 的授权记录存在 SharedPreferences 里，**卸载会一起清掉** —— 重装后要**重新选一次数据目录**
  > 才会回到 SAF 模式（文件还在原目录里，不会丢）。
- **读取范围**：启动 / 回前台 / 切目录都会重扫目录下**所有** `.jsonl`（含旧版 `records.jsonl`，
  以及目录里其它来源的 `.jsonl`，只读合并）；删除与压缩只动 `records*.jsonl`。
- **迁移**：① `filesDir` 根目录的旧 `*.jsonl` → `filesDir/hypergym/`；
  ② SAF 目录里的旧单文件 `records.jsonl` → 新分片。两段都是「先合并、成功后删旧」。
- **删除联动**：日记页删除某天记录 → 内存索引移除 → 全量重写数据文件（失败则回滚内存），
  数据 / 肌群 / 日记三页立即刷新。

### 动作分类如何与手环保持一致（自动同步）

手机端记录的每个动作名都来自手环 payload（手机没有手工录入入口），所以「动作属于哪个部位」
必须以手环动作表为准。`data.js` 里每个动作都显式带了 `group`，它就是**唯一权威来源**。

实现方式：**构建期自动生成**，不需要手工同步。

```
miband10pro-trainer/src/common/data.js      ← 手环动作表（唯一权威来源）
        │  tools/sync-band-exercises.js      （build-debug.ps1 每次构建手机端前自动执行）
        ▼
phone-app/.../data/BandExercises.kt          ← 自动生成的 Kotlin 常量（勿手改）
        │
        ▼
phone-app/.../data/MuscleMap.kt              ← 分类：查表 → 历史别名 → 关键词
```

**以后只要在 `data.js` 里增减动作或改 `group`，手机 APK 会跟着变**，无需手动改 Kotlin。
生成器会校验并直接中止构建：动作重名、`group` 不在 `GROUP_ORDER` 里、`data.js` 结构变化等
异常都不会被静默打进包里；动作被移除时还会提醒去 `MuscleMap` 的 `LEGACY_ALIASES`（或关键词）
补上历史映射 —— 旧记录里可能还有那个名字，不补就会掉进「其他」。

手动执行：

```bash
node tools/sync-band-exercises.js            # 生成/更新（打印新增/删除/改分类的差异）
node tools/sync-band-exercises.js --check    # 只校验是否同步，漂移则 exit 1
```

> 为什么生成 Kotlin 而不是 assets JSON：生成 Kotlin 是编译期常量，分类不再需要 `Context`，
> 也不存在「没初始化就静默降级」的顺序依赖。旧实现曾用 1324 条英文动作库做模糊匹配，
> 且 `init()` 只在肌群页被调用过 —— 没进过肌群页就会退化成纯关键词匹配，同一个动作的分类
> 取决于用户点过哪些页面；模糊匹配本身也会误判（26 个动作里有 6 个分错，例如「水平胸推」
> 被匹配成「后水平」而算作**背**）。现在改为精确查表，两个问题一并消失。

## 应用图标

图标由 `logo/` 下的 SVG 生成，**分两层**（Android 自适应图标结构）：

| 层 | 内容 | 来源 |
|---|---|---|
| `ic_launcher_background` | 橙色渐变 + soft-light 纹理 | `logo/back.svg` 的渐变 + `front.svg` 里的纹理 |
| `ic_launcher_foreground` | 11 个纯白矢量图元（哑铃），透明底 | `logo/front.svg` |

**为什么纹理必须留在背景层**：`front.svg` 里的纹理用的是 `mix-blend-mode: soft-light`，它的混合底就是那层渐变。
若把纹理挪到透明的前景层，会因为「无底色可混合」而露出脏斑。两层叠加后与原始 SVG 完全一致。

**尺寸与安全区**：自适应图标只显示中心 **72/108**，绝对安全区是 **66dp 的圆（占画布 61.1%）**。
实测本图标哑铃占画布宽 **49.1%**，完整落在安全圆内，因此任何遮罩形状都不会裁到图形。

> 未采用 `front2.svg`：它的哑铃占宽 **72.7%**，超出 66.7% 的可见区，圆形遮罩会切掉最外侧的配重片。
> 两者是同一幅作品的等比例放大（长宽比 2.04 : 2.03），所以缩到安全尺寸后结果与现用的一致。

**资源清单**（5 个密度 × 4 个文件，均为 PNG）：

```
mipmap-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}/
  ic_launcher.png             48dp  传统图标（满幅作品，未裁切）
  ic_launcher_round.png       48dp  同上
  ic_launcher_background.png 108dp  自适应背景层（满幅不透明）
  ic_launcher_foreground.png 108dp  自适应前景层（透明底 + 哑铃）
mipmap-anydpi-v26/
  ic_launcher.xml, ic_launcher_round.xml   自适应图标定义
```

> 密度变体由 432×432 / 1024×1024 的母版**面积平均重采样**得到（不是逐尺寸渲染）。
> 面积平均是缩小的正确算法；且重采样时颜色按 alpha 预乘后再平均，避免透明边缘出现黑边。

**生成时必须注意的一点**：渲染页要用**固定像素定位**（`position:fixed; left:0; top:0; width:Npx`），
**不要用 `100vw/100vh`**。Chrome 在 Windows 上会把窗口宽度钳制到约 499px：请求宽度小于该值时，
容器变成非正方形，方形 SVG 会按 `xMidYMid` 在更宽容器里水平居中，截图再从左裁切 —— 内容整体右移
`(499 − 请求宽度)/2`。v3.1.14 就是这样把哑铃画歪了 33.5px。
**每个产物都必须校验居中**（图形边界框中心 = 画布中心，容差 ±0.5px）。

  `drawable-v24/ic_launcher_foreground.xml`、`drawable-nodpi/logo_fg.png`（约 119 KB）

**修复：数据页「容量趋势」卡片在「月」档的日期顺序反了**

  （`monthTrendPoints` 用了 `(endDay downTo 1)`），已改为升序
- **打开或刷新后自动聚焦到最新日期**（滚到最右端），与「动作数据汇总」「数据透视」保持一致

**性能优化（数据透视）**

数据透视的重算复杂度原本是 **O(桶 × 序列 × 记录)** —— `valueOf()` 每次调用都对全量记录做一次
`filter`，而它被调用「桶数 × 序列数」次。更糟的是 `bucketKey` 写在过滤条件里反复求值，
当 **X 轴选「周」** 时，每次求值都要走一次
`Calendar.getInstance()` + `SimpleDateFormat.parse` + `format`。

耗时对比（V8 实测，真机 ART 会更慢；已用 1120 个参数组合验证输出完全不变）：

| 数据透视设置 | 200 天 / 584 条记录 | |
|---|---:|---:|
| | 优化前 | 优化后 |
| 周 × 动作 × 多项 | 450.0 ms | **0.37 ms（快 1230×）** |
| 日期 × 动作 × 多项 | 7.4 ms | **0.29 ms（快 26×）** |
| 日期 × 肌群 × 多项 | 3.7 ms | **0.14 ms（快 27×）** |
| 日期 × 动作 × 单项 | 0.8 ms | **0.07 ms（快 11×）** |

改法：

- **每条记录只算一次**分桶键/序列键，不再在过滤条件里反复求值
- 一次遍历直接建 `桶 → 序列 → 日期 → 记录` 索引，`valueOf` 退化为 O(1) 查表，整体降到 **O(记录数)**
- 「所在周的周一」改用纯整数算法（Howard Hinnant 的 `days_from_civil` / `civil_from_days`），
  **不再经过 `SimpleDateFormat` / `Calendar`**；已对 1970-01-01 ~ 2035-12-31 共 24106 天与旧实现逐日比对，结果一致
- 顺带移除了 `PivotCard` 对 `StatsEngine` 日期格式化的依赖（那个 `SimpleDateFormat` 是全进程共享实例，
  非线程安全，见 [`REVIEW.md`](REVIEW.md) M5）

输出口径完全未变：分桶/序列顺序取首次出现序，排序保持稳定，「先按天求指标、再对天求和/平均」照旧。

> 剩余的性能问题（切页跨页动画、非惰性柱状图、Canvas 逐帧测量文字、数据快照导致全量重算）
> 已记入 [`TODO.md`](TODO.md) §②，按批次待办。
